## 4. Forward migration and role ordering

Select one forward production migration: `V3__outbox_recovery.sql`. The admin-run POC bootstrap creates the new roles and establishes **Decision 17's stable** `vra_owner → vra_async_executor` membership with `SET TRUE, INHERIT FALSE, ADMIN FALSE`, plus database CONNECT and prerequisite schema USAGE. Both endpoint roles are NOLOGIN; the membership is for exact guarded-function ownership management, not runtime delegation, worker privilege, staff authorization, or production impersonation. The accepted `vra_migrator → SET ROLE vra_owner` migration path remains unchanged and needs no CREATEROLE. No V3 role-membership grant/revoke or post-migration admin cleanup is planned.

The exact dependency-safe V3 transaction order is: (1) start under the accepted migrator/owner path after admin bootstrap; (2) create the seven tables; (3) create static FK/CHECK/UNIQUE constraints and indexes; (4) create lifecycle SECURITY DEFINER functions and ordinary/constraint-trigger helper functions initially owned by `vra_owner`, with fixed safe search paths, qualified references, validated arguments, and no dynamic SQL; (5) revoke PUBLIC EXECUTE immediately, before any caller grant; (6) `CREATE TRIGGER` and `CREATE CONSTRAINT TRIGGER` while `vra_owner` still owns both target tables and referenced helper functions, so table TRIGGER and helper EXECUTE authority come from that ownership; (7) grant `vra_async_executor` **temporary schema CREATE** inside V3 solely for `ALTER FUNCTION ... OWNER TO`; (8) transfer the exact guarded and required helper functions using Decision 17's stable SET path; (9) revoke executor schema CREATE **before commit**; (10) grant exact executor table/sequence rights and caller-specific EXECUTE; (11) assert `pg_proc` ownership, `pg_auth_members` options, schema/table/sequence/function ACLs, and PUBLIC EXECUTE denial where practical; (12) commit atomically. The stable role-membership edge remains; the temporary **schema CREATE grant does not**. Every referenced trigger function exists before trigger binding, and binding precedes helper ownership transfer; no executor table TRIGGER grant or post-commit admin cleanup is needed.

The bootstrap roles are `vra_outbox_worker`, `vra_reconciliation_worker`, `vra_async_operator`, `vra_projection_rebuilder`, `vra_async_observer` (LOGIN, NOINHERIT, no owner/capability membership) and `vra_async_executor` (NOLOGIN, NOINHERIT, non-owner, no superuser/CREATEDB/CREATEROLE). Operator, rebuilder, and observer are bounded POC test/admin callers only; they do not claim production staff authentication. The existing three roles and V1/V2 are unchanged. Fresh migration and actual V2→V3 upgrade both preserve existing reservation/idempotency rows; upgrade does **not** retroactively emit events for historical reservations. Migration validation/rerun and checksum tests use disposable PostgreSQL.

All V3 objects live in `vra` and are owned by `vra_owner`, except the explicitly named guarded SECURITY DEFINER functions and required narrow trigger helpers, owned by `vra_async_executor`. No new schema is needed. Executor steady state is NOLOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE; it owns no schema/table, has no schema CREATE, DELETE, TRUNCATE, table/schema DDL, or table/schema GRANT option, and has only the table/sequence access required by those functions. ## 5. Exact relational model

Use UUID identifiers for event, delivery claim, case, and reconciliation claim. Java generates opaque event UUID v4; PostgreSQL `pg_catalog.gen_random_uuid()` generates claim/case UUIDs. Use `pg_catalog.statement_timestamp()` for operational transitions/eligibility and `TIMESTAMPTZ` throughout. Durations enter functions as validated positive integer milliseconds, then PostgreSQL anchors them to its statement time. All status/reason columns use bounded text plus explicit CHECKs; no PostgreSQL enum that would force an unrelated type migration for this POC. Every timestamp below except event `occurred_at` is PostgreSQL coordination/operational time. `reason_code` is an allowlisted stable code, never raw exception text.

**`vra.outbox_event` — immutable intent.** `event_id UUID NOT NULL PRIMARY KEY`; `event_type VARCHAR(128) NOT NULL`; `schema_version INTEGER NOT NULL`; `occurred_at TIMESTAMPTZ NOT NULL`; `reservation_id UUID NOT NULL UNIQUE REFERENCES vra.inventory_reservation(reservation_id)`; `sku_id UUID NOT NULL`; `owner_id UUID NOT NULL`; `location_id UUID NOT NULL`; `stock_status VARCHAR(32) NOT NULL`; `quantity BIGINT NOT NULL`. Checks: nonblank type, positive schema version and quantity, `stock_status IN ('AVAILABLE','QUARANTINED')`, `event_id <> reservation_id`. The six last business columns are the logical payload; no JSONB or other event fields. The unique reservation ID enforces at most one event for the authoritative creation. Producer function fixes the selected type/version and copies all business columns plus `created_at` from the just-flushed reservation. An unconditional BEFORE UPDATE/DELETE trigger rejects rewrites/deletes, including accidental privileged DML. No ordinary worker DELETE authority; no permanent event-store claim. Index: unique reservation ID (implicit unique index).

**`vra.outbox_delivery` — current delivery.** `event_id UUID PRIMARY KEY REFERENCES vra.outbox_event(event_id)`; `target_code VARCHAR(40) NOT NULL` checked to `RESERVATION_PROJECTION` or `VALIDATION_EXTERNAL_EFFECT`; `state VARCHAR(32) NOT NULL`; `failure_class VARCHAR(32) NULL`; `reason_code VARCHAR(64) NULL`; `next_eligible_at TIMESTAMPTZ NULL`; `claim_token UUID NULL`; `claim_until TIMESTAMPTZ NULL`; `claim_relinquished BOOLEAN NOT NULL DEFAULT FALSE`; `delivery_attempt_count BIGINT NOT NULL DEFAULT 0`; `automatic_cycle INTEGER NOT NULL DEFAULT 1`; `cycle_claim_count INTEGER NOT NULL DEFAULT 0`; `cycle_claim_limit INTEGER NOT NULL`; `created_at TIMESTAMPTZ NOT NULL`; `state_changed_at TIMESTAMPTZ NOT NULL`. Producer function initializes `(automatic_cycle,cycle_claim_count,cycle_claim_limit)=(1,0,5)`. Row-local CHECKs enforce known states/classes, `automatic_cycle >= 1`, `cycle_claim_count >= 0`, `cycle_claim_limit BETWEEN 1 AND 16`, `cycle_claim_count <= cycle_claim_limit + 1`, and count above limit only in non-dispatching FAILED/RECONCILIATION_REQUIRED/SUCCEEDED/CLOSED rows; they also enforce READY/RETRY_WAIT/PROCESSING/RECONCILIATION_REQUIRED/SUCCEEDED/FAILED/CLOSED reason and eligibility shapes and no claim on terminal/failed/reconciliation-required rows. A committed dispatchable PROCESSING row must have `cycle_claim_count <= cycle_claim_limit`. SUCCEEDED may retain recovery-only count after reconciliation confirms the prior external effect. PROCESSING has token+lease; relinquished PROCESSING remains PROCESSING but cannot finalize. READY has no claim and no reason; RETRY_WAIT requires RETRYABLE_TRANSIENT reason and eligibility; RECONCILIATION_REQUIRED requires UNKNOWN_OUTCOME reason; FAILED requires stable failure class/reason; CLOSED requires explicit closure reason. Indexes: `(target_code, state, next_eligible_at, created_at, event_id)` for READY/RETRY_WAIT; `(target_code, claim_until, event_id)` partial on PROCESSING; unique non-null current claim token; `(state, created_at)` for backlog age. Immutable columns are `event_id`, `target_code`, `created_at`; cycle limit changes only through controlled new-cycle function, and all other updates are function-only.

**`vra.outbox_delivery_history` — append-only evidence.** `history_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`; `event_id UUID NOT NULL REFERENCES vra.outbox_event`; `action_code VARCHAR(40) NOT NULL`; `from_state VARCHAR(32) NULL`; `to_state VARCHAR(32) NOT NULL`; `claim_token UUID NULL`; `lifetime_attempt BIGINT NOT NULL`; `automatic_cycle INTEGER NOT NULL`; `cycle_claim_count INTEGER NOT NULL`; `cycle_claim_limit INTEGER NOT NULL`; `failure_class VARCHAR(32) NULL`; `reason_code VARCHAR(64) NULL`; `actor_kind VARCHAR(24) NOT NULL`; `actor_ref VARCHAR(128) NULL`; `recorded_at TIMESTAMPTZ NOT NULL`. Checks bound codes/counts and `cycle_claim_limit BETWEEN 1 AND 16`; actor reference is diagnostic only. Indexes `(event_id,history_id)` and unique `claim_token` where `action_code IN ('CLAIM','RECLAIM')`. Each row preserves the cycle/limit/count/lifetime/action/reason of that transition, including recovery-only and controlled replay; old rows never change. UPDATE/DELETE trigger rejects mutation. Initial READY creation has a history row. History is operational, not protected audit.

**`vra.consumer_inbox` — dedup.** `consumer_identity VARCHAR(64) NOT NULL`; `event_id UUID NOT NULL`; `processed_at TIMESTAMPTZ NOT NULL`; PRIMARY KEY `(consumer_identity,event_id)`. Check nonblank consumer identity. No universal FK to local outbox. Consumer worker may SELECT/INSERT directly; no UPDATE/DELETE. Timestamp is PostgreSQL time. The row is inserted inside the same transaction as projection insertion; rollback removes both.

**`vra.reservation_projection` — derived data.** `reservation_id UUID PRIMARY KEY REFERENCES vra.inventory_reservation(reservation_id)`; `sku_id UUID NOT NULL`; `owner_id UUID NOT NULL`; `location_id UUID NOT NULL`; `stock_status VARCHAR(32) NOT NULL`; `quantity BIGINT NOT NULL`; `projected_at TIMESTAMPTZ NOT NULL`. Check positive quantity and known status; index `(sku_id,owner_id,location_id,stock_status)`. No `source_event_id`: provenance is optional and authoritative reservations cannot reconstruct it. Consumer may SELECT/INSERT, not UPDATE/DELETE. Controlled rebuild function may SELECT/INSERT/UPDATE through its owner. The FK rules out projection-only reservation IDs; no prune/DELETE capability is required. Business content is never used for Inventory/Reservation decisions.

**`vra.reconciliation_case` — current per-item checkpoint.** `case_id UUID PRIMARY KEY`; `event_id UUID NOT NULL REFERENCES vra.outbox_delivery(event_id)`; `state VARCHAR(32) NOT NULL`; `external_knowledge VARCHAR(32) NOT NULL`; `reason_code VARCHAR(64) NOT NULL`; `next_eligible_at TIMESTAMPTZ NULL`; `claim_token UUID NULL`; `claim_until TIMESTAMPTZ NULL`; `lifetime_attempt_count BIGINT NOT NULL DEFAULT 0`; `automatic_cycle INTEGER NOT NULL DEFAULT 1`; `cycle_claim_count INTEGER NOT NULL DEFAULT 0`; `cycle_claim_limit INTEGER NOT NULL`; `created_at TIMESTAMPTZ NOT NULL`; `state_changed_at TIMESTAMPTZ NOT NULL`. UNKNOWN handoff creates `(automatic_cycle,cycle_claim_count,cycle_claim_limit)=(1,0,4)`. Partial UNIQUE `(event_id)` where state is PENDING/CHECKING/WAITING/OPERATOR_REQUIRED. Row-local CHECKs enforce valid state/knowledge, `automatic_cycle >= 1`, `cycle_claim_count >= 0`, `cycle_claim_limit BETWEEN 1 AND 16`, `cycle_claim_count <= cycle_claim_limit + 1`, and count above limit only in non-querying OPERATOR_REQUIRED/CLOSED. A committed query-bearing CHECKING row must remain at or below its durable limit. PENDING/WAITING have durable eligibility, CHECKING has token+lease, RESOLVED/OPERATOR_REQUIRED/CLOSED have no active claim/eligibility, confirmed knowledge is only in RESOLVED, and unresolved/closed knowledge is UNKNOWN. Indexes `(state,next_eligible_at,case_id)` for PENDING/WAITING, `(claim_until,case_id)` partial on CHECKING, and `(state,created_at)` for operator backlog. `case_id`, `event_id`, `created_at` immutable; cycle limit changes only through controlled resume, and other writes are function-only. A later uncertain episode inserts a new case.

**`vra.reconciliation_history` — append-only evidence.** `history_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`; `case_id UUID NOT NULL REFERENCES vra.reconciliation_case(case_id)`; `action_code VARCHAR(40) NOT NULL`; `from_state VARCHAR(32) NULL`; `to_state VARCHAR(32) NOT NULL`; `claim_token UUID NULL`; `lifetime_attempt BIGINT NOT NULL`; `automatic_cycle INTEGER NOT NULL`; `cycle_claim_count INTEGER NOT NULL`; `cycle_claim_limit INTEGER NOT NULL`; `observation VARCHAR(32) NULL`; `reason_code VARCHAR(64) NOT NULL`; `actor_kind VARCHAR(24) NOT NULL`; `actor_ref VARCHAR(128) NULL`; `recorded_at TIMESTAMPTZ NOT NULL`. Checks constrain codes/counts and `cycle_claim_limit BETWEEN 1 AND 16`; index `(case_id,history_id)` and unique claim token for claim/reclaim actions. Each row records cycle/limit/count/lifetime/action/observation/reason; old-cycle evidence never changes. UPDATE/DELETE trigger rejects mutation.

V3 also installs a DEFERRABLE INITIALLY DEFERRED reconciliation-pair constraint trigger on delivery/case INSERT/UPDATE/DELETE. At commit, RECONCILIATION_REQUIRED has exactly one matching active PENDING/CHECKING/WAITING case; FAILED with an unresolved case has exactly one OPERATOR_REQUIRED case; other delivery states have no active case. It runs under the constrained capability owner with only needed SELECT, so compound function transactions can change both rows before the commit check. The active-case partial unique index independently prevents two unresolved cases. Tests must reject malformed shapes and orphan/mismatched pairs even when an owner-level test fixture tries direct DML. Do not use this trigger to perform lifecycle transitions.

A second **deferred constraint-trigger/helper mechanism**, rather than a PostgreSQL CHECK, validates the cross-table evidence: a delivery/case current row at `cycle_claim_count = cycle_claim_limit + 1` must have a matching immutable `RECOVERY_ONLY_*` history action in the same cycle at commit. Row-local CHECKs exclude count-above-limit PROCESSING/CHECKING and all counts above limit+1. Only the guarded recovery-only functions can append the required action and leave the non-dispatching state in one transaction. Controlled closure may retain that old count and history; controlled replay/resume resets only the new cycle count. Executor receives SELECT on both histories solely for this deferred check.

The state-shape CHECK expressions encode this nullability matrix in addition to the allowed state/class code sets:

| --- | --- | --- | --- |
| READY | both NULL; relinquished FALSE | NULL | both NULL |
| PROCESSING | both non-NULL; relinquished TRUE/FALSE | NULL | both NULL |
| RETRY_WAIT | both NULL; relinquished FALSE | non-NULL | RETRYABLE_TRANSIENT and non-NULL reason |
| RECONCILIATION_REQUIRED | both NULL; relinquished FALSE | NULL | UNKNOWN_OUTCOME and non-NULL reason |
| SUCCEEDED | both NULL; relinquished FALSE | NULL | both NULL |
| FAILED | both NULL; relinquished FALSE | NULL | non-NULL stable class and reason |
| CLOSED | both NULL; relinquished FALSE | NULL | previous failure class may remain; explicit closure reason non-NULL |

| Case state | Current token and lease | `next_eligible_at` | External knowledge |
| --- | --- | --- | --- |

## 6. Event representation and producer integration

Typed columns are selected over JSONB because this bounded POC has one immutable creation contract, six known fields, and benefits from native FK/CHECK/UNIQUE validation without accepting arbitrary request metadata. `ReservationCreatedEventV1` exposes `eventId`, constant `inventory.reservation.created`, version `1`, `occurredAt`, and a payload record of exactly `reservationId,skuId,ownerId,locationId,stockStatus,quantity`. Codec output uses lower-camel JSON names, canonical lowercase UUID strings, enum name, integer quantity, and UTC ISO-8601 instant; it validates exact supported type/version and required fields before any inbox or external effect. The storage row is never rewritten to adapt a consumer. Unsupported type/version is classified POISON, durably FAILED with safe reason, never silently acknowledged.

Modify `ReservationExecution.execute` once: after the existing conditional stock update succeeds, generate reservation UUID and `createdAt = Instant.now(clock)` once, persist/flush `InventoryReservation`, then call `ReservationOutboxPort.publish(reservation)` before returning success. The port implementation generates a distinct Java UUID v4 `eventId` and invokes `vra.async_publish_reservation(eventId,reservationId,targetCode)` through the same Spring transaction/data source. The function reads the flushed authoritative reservation row, validates the target, inserts fixed type/version plus six fields and reservation `created_at`, inserts one READY delivery, and appends initial delivery history. No separate transaction or AFTER COMMIT callback is used. Any insert/function failure propagates to roll back inventory, reservation, and applicable idempotency state.

`ReservationApplicationService.reserve` retains its current outer transaction. `IdempotentReservationApplicationService.reserve` retains its READ_COMMITTED transaction and invokes shared execution only after a first authoritative claim; its terminal `SUCCEEDED` completion follows shared execution in the same transaction. Replay/conflict/controlled rejection/prevalidation never call the producer. Neither path gains caller reservation ID, caller `expectedVersion`, public actor binding, synchronous projection write, or external call. Producer target is a validated process property fixed for the POC scenario at startup, not a subscription/routing table; production/API default is `RESERVATION_PROJECTION`, and `VALIDATION_EXTERNAL_EFFECT` is accepted only under the explicit POC validation mode. The persisted target is immutable, so changing process configuration cannot redirect an already committed event.

### 7.1 Narrow operation catalog

All functions are `vra.`-qualified, owned by `vra_async_executor`, and called in a short Spring/JDBC transaction under the indicated credential. Each function locks the relevant current row(s), checks exact source state and ownership, makes only the listed transition, and appends delivery/reconciliation history in that **same** transaction. For paired changes, it locks delivery before case by `event_id` to maintain one lock order; the deferred pair trigger validates the committed shape. `TRUE` means exactly one guarded operation committed; `FALSE` means stale/ineligible with zero mutation. Claims return only newly committed claim rows; empty means no eligible work. The JDBC adapter asserts expected rows and treats false/empty as a non-effect, not as an invitation to execute externally.

### 7.2 SQL body pattern and code vocabulary

V3 defines the function bodies as PL/pgSQL operation transactions. The following body pattern is exact for every single-row transition: validate arguments; `SELECT ... FROM vra.outbox_delivery WHERE event_id=p_event_id FOR UPDATE` (and, for paired operations, `SELECT ... FROM vra.reconciliation_case WHERE case_id=p_case_id AND event_id=... FOR UPDATE` **after** the delivery lock); return `FALSE`/NULL if the source-state, current token, non-relinquished flag, matching case/knowledge, or **persisted** limit/count guard fails; perform an `UPDATE ... WHERE event_id=:id AND state=:source AND claim_token=:token AND NOT claim_relinquished RETURNING ...` where claim-owned; require exactly one returned row; insert the required history row(s) including cycle/limit/count; return the declared result. All statements run in the caller's transaction; any insert/check failure raises and rolls back everything. Paired functions update delivery and case under the same locks; no autonomous transaction exists. Controlled functions use the same pattern without token but with exact FAILED/case/UNKNOWN guards and DB-fixed new-cycle limits. `async_publish_reservation` instead uses `INSERT INTO vra.outbox_event(...) SELECT p_event_id,'inventory.reservation.created',1,r.created_at,r.reservation_id,... FROM vra.inventory_reservation r WHERE r.reservation_id=p_reservation_id`, checks one inserted row, then inserts READY delivery with cycle/count/limit `1/0/5` and creation history. It accepts no payload/state/type/version/budget arguments. Claim functions use the locked candidate body in §8, set `claim_token=pg_catalog.gen_random_uuid()`, `claim_until=pg_catalog.statement_timestamp()+p_lease_ms*INTERVAL '1 millisecond'`, increment both applicable counts, and append claim history before returning **only** dispatchable claims. Recovery-only claims instead append their terminal/handoff action and return nothing in the same transaction. Rebuild uses the locked `INSERT ... SELECT ... ON CONFLICT(reservation_id) DO UPDATE` body in §11. No lifecycle function calls `SET ROLE`, builds SQL text dynamically, or catches a constraint exception to pretend success.

V3 CHECKs constrain history `action_code` to the exact delivery set `CREATED,CLAIM,RECLAIM,RELINQUISH,SUCCEEDED,RETRY_SCHEDULED,FAILED,UNKNOWN_HANDOFF,RECOVERY_ONLY_FAILED,RECOVERY_ONLY_UNKNOWN_HANDOFF,RECONCILED_SUCCESS,RECONCILED_NO_EFFECT,RECONCILIATION_EXHAUSTED,CONTROL_REPLAY,CONTROL_RESUME,CONTROL_CLOSE` and reconciliation set `CREATED,CHECK_CLAIM,CHECK_RECLAIM,INDETERMINATE_WAIT,CONFIRMED_SUCCESS,CONFIRMED_NO_EFFECT,EXHAUSTED,RECOVERY_ONLY_EXHAUSTED,CONTROL_RESUME,CONTROL_CLOSE`. The recovery-only claim logs its claim token/count and its specific non-dispatching action at count = limit+1; the deferred evidence check looks for that action in the same cycle. `reason_code` has CHECK `^[A-Z][A-Z0-9_]{0,63}$`; operation functions accept only stable codes appropriate to that operation (for example `UNKNOWN_EXTERNAL_RESULT`, `RECLAIM_POSSIBLE_EXTERNAL_SEND`, `RETRYABLE_TRANSIENT`, `RETRY_EXHAUSTED`, `UNSUPPORTED_EVENT_CONTRACT`, `NON_RETRYABLE`, `POISON`, `OPERATOR_REQUIRED`, `RECONCILIATION_EXHAUSTED`, `CONTROLLED_REPLAY`, `CONTROLLED_RESUME`, `CONTROLLED_CLOSE`). The application maps failures to these codes and keeps raw exception text out of rows. `actor_ref`/`action_ref` are bounded diagnostic references, never authorization evidence. Case `observation` CHECK permits NULL, CONFIRMED_SUCCEEDED, CONFIRMED_NO_EFFECT, INDETERMINATE only.

V3 grants `USAGE ON SCHEMA vra` to the new roles and capability owner; executor's temporary CREATE is revoked before V3 commits. ## 8. Claim, reclaim, and safe relinquishment mechanics

`async_claim_delivery` uses one SQL statement/short transaction shaped as: candidate `SELECT event_id FROM vra.outbox_delivery WHERE target_code=:target AND ((state='READY' AND cycle_claim_count<cycle_claim_limit) OR (state='RETRY_WAIT' AND next_eligible_at<=statement_timestamp() AND cycle_claim_count<cycle_claim_limit) OR (state='PROCESSING' AND cycle_claim_count<=cycle_claim_limit AND (claim_until<=statement_timestamp() OR claim_relinquished))) ORDER BY COALESCE(next_eligible_at,claim_until,created_at),created_at,event_id FOR UPDATE SKIP LOCKED LIMIT :batch`; update only selected rows after reading their locked persisted limit. For normal claims, generate token with `pg_catalog.gen_random_uuid()`, set PROCESSING/lease/counts, append history, and return only rows whose new count is at most their durable limit. For recovery-only rows, take the distinct direct-to-non-dispatching branch below. The query and function hold locks only until this DB transaction commits. Workers start consumer/external processing afterward. PostgreSQL READ COMMITTED is retained; no global isolation change. Batch bounds are checked by both startup validation and function.

On expired/relinquished PROCESSING, the new committed token alone transfers ownership for a **normal returned** claim. The returned `reclaimed=true` is derived from locked prior state, not a durable phase marker. Scenario A may redeliver through inbox. Scenario B must call `async_handoff_unknown` before any external execute, then the reconciler performs query-only observation. If C2 dies after reclaim but before handoff, C3 again reclaims PROCESSING and follows the same rule; no missing local marker can imply no effect. At locked `cycle_claim_count=cycle_claim_limit` on an expired/relinquished PROCESSING row, the function permits **one final recovery-only claim**: it generates a fresh fencing token, increments lifetime and cycle counts once to limit+1, and writes the claim and specific Scenario A FAILED or Scenario B UNKNOWN-handoff histories in the **same transaction**. It updates the current row directly from the locked prior PROCESSING state to the non-dispatching outcome; it never writes a count-above-limit PROCESSING row, even transiently, and never returns a dispatchable token. This atomic fenced recovery operation creates no separately usable processing ownership. Normal claims never exceed the persisted limit of **5 execution-bearing claims**; total automatic claims cannot exceed 6. No repeated recovery-only claim is possible because the committed state is neither claimable PROCESSING nor READY/RETRY_WAIT. Normal retry scheduling never produces RETRY_WAIT when the execution-bearing budget is exhausted; no worker configuration can increase that bound.

Relinquishment uses `claim_relinquished=true` plus `claim_until=LEAST(claim_until,statement_timestamp())`. It keeps state PROCESSING and the old token for history, but every finalize function checks `NOT claim_relinquished`; the claim function can replace it with a new token only in a committed reclaim. No PROCESSING→READY transition, outcome classification, or direct ownership transfer occurs. Failed/aborted relinquishment leaves the old durable lease untouched for normal expiry fallback. Scenario B's reclaimed flag remains true after relinquishment and routes to reconciliation first. A stale finalizer gets `FALSE`; it never appends a successful transition history row. A stale reconciler likewise gets `FALSE`.

`async_claim_reconciliation` uses a bounded candidate join over due PENDING/WAITING with `cycle_claim_count<cycle_claim_limit` and expired CHECKING with `cycle_claim_count<=cycle_claim_limit`, ordered by `COALESCE(c.next_eligible_at,c.claim_until,c.created_at),c.created_at,c.case_id`, with `FOR UPDATE OF d SKIP LOCKED` on the matching delivery `d` **first**. It then locks each candidate case `c FOR UPDATE`, rechecks eligibility and its persisted limit, and changes both records in delivery-then-case lock order. This prevents the claim path from inverting the lock order of paired finalizers. When no case is eligible, no process-local cursor holds responsibility. An expired CHECKING row at count=limit permits one final non-querying recovery claim: generate fresh fencing token, increment lifetime/cycle counts once to limit+1, and write claim plus specific recovery-only history while directly changing the locked case to OPERATOR_REQUIRED and delivery to FAILED/UNKNOWN in the **same transaction**. It never writes count-above-limit CHECKING, even transiently, and returns no queryable claim. Normal case claims cannot exceed the persisted **4 query-bearing claims**, and total automatic claims cannot exceed 5. Repeated recovery-only claims are impossible after the committed state leaves CHECKING. Reconciliation network observation starts only after a query-bearing claim transaction commits.

## 9. Retry, FAILED work, replay, and configuration policy

Use failure classifications `RETRYABLE_TRANSIENT`, `NON_RETRYABLE`, `UNKNOWN_OUTCOME`, `POISON`, and `OPERATOR_REQUIRED` as distinct Java/DB codes. A caught exception is not automatically retryable. Scenario A transient DB/consumer errors that rolled back their effect may retry; committed inbox effects are deduplicated. Scenario B timeout, lost response, or any send ambiguity is UNKNOWN and goes to reconciliation; only provable before-send validation failures may be classified safe transient/non-retryable. Unsupported event type/version is POISON and never inserted as successful inbox processing.

Select bounded POC **runtime tuning** defaults (not production tuning): `leaseDuration=30s`; `processingTimeout=10s`; `retryBaseDelay=200ms`; `retryMaxDelay=5s`; `retryJitterFraction=0.20`; `pollInterval=200ms`; `batchSize=8`; `maxInFlight=8`; `reconciliationLeaseDuration=30s`; `reconciliationTimeout=10s`; `reconciliationBaseDelay=500ms`; `reconciliationMaxDelay=5s`. Only these timing/concurrency values are configurable under `vra.async.*`; use typed `Duration`/positive integers. **Decision 16 fixes the POC cycle limits in guarded DB operations**: delivery 5 and reconciliation 4, persisted when each cycle begins. They are not worker/reconciler runtime properties or caller arguments. Any application constant is diagnostic/startup consistency only and cannot redefine a row's current limit. Startup rejects nonpositive/overflow values, `processingTimeout >= leaseDuration`, `reconciliationTimeout >= reconciliationLeaseDuration`, max delay below base, jitter outside `[0,0.5]`, batch above max in-flight, and wrong DB role for selected mode. A worker's bounded executor capacity and semaphore equal `maxInFlight`; it never claims more rows than free capacity. Runtime timing defaults allow a local POC and can be overridden in disposable tests; no numeric production SLO is asserted.

Application policy computes `min(maxDelay, baseDelay × 2^(cycleClaimCount−1)) × (1+jitter)` with jitter sampled uniformly in `[-0.20,+0.20]`. Inject a `JitterSource` interface; deterministic tests use a fixed/seeded source. Clamp safely to positive milliseconds and reject overflow. Database functions anchor that duration using `statement_timestamp()`. POC tests can use disposable admin fixtures to move durable eligibility timestamps into the past and then assert PostgreSQL claim behavior, plus short bounded real-time probes; they never substitute a JVM Clock for lease authority or sleep for long intervals. No heartbeat/lease renewal is added.

`delivery_attempt_count` is monotonic for the event lifetime. `automatic_cycle`, `cycle_claim_count`, and persisted `cycle_claim_limit` bound one automatic run. A controlled FAILED→READY replay increments the cycle, resets count to 0, writes limit 5, and retains lifetime attempt count plus all old history; ordinary worker calls cannot alter the limit. Confirmed-no-effect RETRY_WAIT continues the **same** delivery cycle and persisted limit. The replay function never bypasses unresolved UNKNOWN. No blind batch replay or retry timer in process memory is authoritative. An exhausted automatic cycle yields durable FAILED with stable reason, except an exhausted crashed Scenario B PROCESSING claim first enters UNKNOWN reconciliation without another external execute. `OPERATOR_REQUIRED` cases are visible backlog, not permission for ordinary delivery claims.

## 10. Scenario A: inbox and projection consumer

`ReservationProjectionConsumer.consume(ReservationCreatedEventV1)` first validates the exact type/version and six required fields. Under `vra_outbox_worker` in a **new Spring transaction** (separate from claim and finalize), it attempts `INSERT INTO vra.consumer_inbox(consumer_identity,event_id,processed_at) VALUES ('reservation_projection_v1',:eventId,statement_timestamp()) ON CONFLICT DO NOTHING RETURNING event_id`. On insertion, it inserts the six business fields into `vra.reservation_projection` with `ON CONFLICT (reservation_id) DO NOTHING`; an existing row from authoritative rebuild is accepted only after a field-by-field equality check against the immutable event, otherwise it fails visibly for repair/review. On inbox conflict, it reads the durable existing inbox row and returns `ALREADY_APPLIED` without a second projection effect. No inbox row is committed before the projection effect; any failure rolls the transaction back. The worker calls guarded delivery success only **after** this consumer transaction commits.

Projection is eventually consistent, never a read-after-write decision source. `projected_at` is operational PostgreSQL time, not an ordering authority. No `inventory_balance.version`, last-write-wins timestamp, or global sequence is used. Different reservation-created events commute by `reservation_id`; duplicate event identity is governed by inbox PK. There is no reservation-update event in v1; generic projection-update testing is NOT APPLICABLE. A crashed worker after inbox/projection commit but before delivery finalize is safely redelivered after reclaim and resolves through the inbox row.

## 11. Controlled projection rebuild

Select **locked upsert repair**, not shadow-table swap or ordinary-worker TRUNCATE. `async_rebuild_reservation_projection` runs as one bounded POC transaction through `vra_projection_rebuilder`. It obtains `LOCK TABLE vra.reservation_projection IN SHARE ROW EXCLUSIVE MODE` so consumer writes cannot interleave; it reads authoritative `vra.inventory_reservation` and upserts all six business fields into projection with `projected_at=statement_timestamp()`. The projection FK prevents rows for nonexistent reservations, so no prune/DELETE is needed. It neither mutates reservations nor reads outbox history nor changes inbox rows. No source-event provenance field is required. For the bounded test dataset, one transaction is acceptable; online/large-scale rebuild is explicitly unproven.

The consumer's projection insert, a rebuild upsert, and a subsequent duplicate/redelivery converge: rebuilt business content is authoritative even if the inbox row already says processed; redelivery does not need to reapply that effect. If a reservation commits after the rebuild source scan, its pending event remains durable and later consumer delivery inserts its missing projection row. The lock serializes any consumer already writing when repair starts. G8 checks damaged/missing rows, preexisting inbox rows, post-rebuild redelivery, new reservations racing around rebuild, and final set equality with the authoritative table. Only the dedicated rebuilder may call this maintenance function; ordinary worker has no DELETE, TRUNCATE, or broad UPDATE privilege.

## 12. Scenario B: validation-only external simulator

Use a separate **test JVM HTTP server** (`SimulatorMain`) backed by a **second, disposable Testcontainers PostgreSQL 17.11 instance** with simulator-owned test schema. Its state and process survive force-killing the worker; it is outside the VRA database and is not part of V3. This reuses Java's JDK HTTP server/client and existing PostgreSQL JDBC/Testcontainers dependencies, adding no production broker or simulator storage dependency. The HTTP adapter is an explicitly POC-only boundary active only for `VALIDATION_EXTERNAL_EFFECT`; no Payment/provider production domain is created.

The simulator exposes test-only `POST /execute`, read-only `GET /operations/{eventId}`, read-only `GET /test/effects/{eventId}`, and health. `eventId` is `externalOperationId`. Its `sim_operation` table has operation UUID PK, canonical semantic payload digest, `PENDING|SUCCEEDED` state, result, and effect count. Accepting execute durably registers PENDING before any test gate; later effect commit makes SUCCEEDED/count 1 under the same operation identity. Same ID+same six-field semantic payload returns/reveals the stored operation and never makes a second effect; same ID+conflicting payload returns explicit 409. Canonical digest is computed from normalized six business fields, not raw JSON formatting, claim token, attempt, or headers. The query endpoint performs no insert/update/effect: SUCCEEDED→CONFIRMED_SUCCEEDED, PENDING→INDETERMINATE, and authoritative absence on the primary DB with no accepted in-flight operation→CONFIRMED_NO_EFFECT. A later-arriving request still carries the same stable ID and is deduplicated. This guarantee is specific to the bounded simulator and is **not** generalized from a real provider's NOT_FOUND.

Test controls allow the server to commit one effect and deliberately drop its HTTP response, or to block an accepted request before effect commit. They are in `src/test` only. The worker can therefore observe response loss/timeout as UNKNOWN while the simulator independently proves the effect count. `ValidationSimulatorHttpAdapter.execute(eventId,payload)` is called only after delivery claim commit. A result that cannot prove no effect is UNKNOWN; it calls atomic UNKNOWN handoff, never `async_retry_delivery`. The reconciler only calls `observe(eventId)` after case claim commit. CONFIRMED_SUCCEEDED resolves; authoritative CONFIRMED_NO_EFFECT allows bounded retry of the **same event ID** if policy proves safe; INDETERMINATE schedules another bounded query. No external call occurs inside a VRA claim/finalize transaction.

For a reclaimed Scenario B PROCESSING attempt, the worker uses the claim result's `reclaimed=true` to call `async_handoff_unknown` **before** any `execute`. It does so even when the prior request may have died just before send. If the worker dies in this gap, subsequent reclaim repeats the same conservative path. Relinquishment never changes this rule. There is no durable sub-state claiming that an invocation definitely never began and no replacement operation identity.

## 13. UNKNOWN, reconciliation, resume, and close

The case row is the durable per-item checkpoint. It stores state, DB-anchored next eligibility, CHECKING token/lease, monotonic lifetime attempt count, and current automatic cycle/count/**limit 4**. There is no correctness-critical scan cursor. On restart, `ReconciliationLoop` queries PostgreSQL again, reads each locked case's persisted limit, and claims eligible PENDING/WAITING/expired CHECKING cases without resetting or increasing that bound; OPERATOR_REQUIRED/UNKNOWN remains visible backlog, not an automatically queryable item. Case IDs differ from delivery tokens and event IDs. One active-case partial unique index plus the deferred pair constraint and function-only DML enforce 0..N historical cases, at most one active unresolved case, and no orphan RECONCILIATION_REQUIRED delivery.

`ReconciliationService` maps only explicit observation results to the narrow functions. Confirmed success atomically resolves case as CONFIRMED_SUCCEEDED and delivery as SUCCEEDED. Confirmed no effect atomically resolves case as CONFIRMED_NO_EFFECT and either schedules same-event RETRY_WAIT under the **existing persisted delivery cycle/limit** (safe, remaining budget) or marks delivery FAILED. INDETERMINATE remains UNKNOWN and WAITING with durable eligibility while case count < its persisted limit; exhaustion makes case OPERATOR_REQUIRED and delivery FAILED while knowledge stays UNKNOWN. A later uncertain retry creates a **new** case at cycle 1/count 0/limit 4, not a reopened RESOLVED case. Stale token/failed history append changes neither side.

The POC `vra_async_operator` caller uses one-event-at-a-time application control code, after inspection, with a stable action reason/reference. No production HTTP replay UI or staff-auth model is claimed. `async_control_replay` alone does FAILED→READY with delivery cycle +1/count 0/limit 5 and unchanged lifetime count; it rejects unresolved UNKNOWN. `async_control_resume` performs FAILED→RECONCILIATION_REQUIRED and OPERATOR_REQUIRED→PENDING together, leaves knowledge UNKNOWN, increments the **case** cycle and resets its count to 0/limit 4 without resetting lifetime attempts/history, and appends both histories. `async_control_close` performs FAILED→CLOSED and, when unresolved, OPERATOR_REQUIRED→CLOSED together while keeping UNKNOWN. Neither resume nor close executes/query external effect. SUCCEEDED/CLOSED are irreversible; controlled operations serialize against late/stale finalizers through row locks and exact guards. Replay, resume, closure, and rebuild have separate capabilities.

## 14. Process modes, bootstrap, and credential isolation

## 15. Graceful drain, bounded work, and visibility

`OutboxWorkerLoop` and `ReconciliationLoop` poll only while accepting claims. A bounded semaphore reserves capacity **before** each claim, with batch limit no greater than free slots; there is no unbounded in-memory queue. Processing/external calls run after claim commit with finite timeout. On drain, set accepting=false first, stop new claims and any new external effect for work not already in-flight, let safe bounded in-flight work finish/finalize, then attempt guarded relinquishment only after an attempt has stopped and safety is established. If it cannot be established or the process dies, leave durable state/lease for expiry recovery. Never synthesize success/failure, change PROCESSING→READY, or make UNKNOWN retry-safe in a shutdown hook. Close JDBC pool/HTTP resources and flush telemetry appropriately. Abrupt death must remain safe without any hook.

`JdbcAsyncVisibility`, under the POC read-only `vra_async_observer` credential, provides grouped counts by persisted target for READY, PROCESSING, RETRY_WAIT, FAILED, RECONCILIATION_REQUIRED, PENDING/CHECKING/WAITING, and OPERATOR_REQUIRED, plus PostgreSQL-time `oldest_outstanding_age` over non-SUCCEEDED/non-CLOSED deliveries for each target. Scenario A backlog/age is the POC projection-freshness signal; Scenario B does not claim a projection. It exposes success/failure/retry activity from append-only delivery and reconciliation histories, including immutable cycle/count/**limit**/lifetime attempt/action/reason evidence so normal exhaustion and recovery-only fencing are distinguishable. Signals use safe codes and opaque IDs, never raw payload/exception/credentials. Use Actuator/Micrometer's existing Spring Boot baseline for bounded process-local counters/gauges and a restricted observer diagnostic query interface; no production dashboard, alert threshold, or SLO is claimed. G11 compares every signal to authoritative SQL at each representative state, including failed/unknown backlog.

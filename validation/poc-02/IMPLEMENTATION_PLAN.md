## 7. Reservation Identity Generation

normal first execution:

```text
validate business command
→ attempt authoritative stock reservation
→ if success: generate UUID reservationId in application transaction
→ persist Reservation
→ return result
```

idempotent first execution:

```text
claim idempotency identity
→ execute reservation decision
→ if success: generate UUID once
→ persist Reservation
→ persist terminal SUCCEEDED result with same UUID
→ commit
```

replay:

```text
read terminal SUCCEEDED
→ return persisted reservationId
→ never generate replacement UUID
```

controller ห้าม generate reservation UUID

## 8. Inventory SQL Refactor

```sql
UPDATE vra.inventory_balance
SET reserved = reserved + :quantity,
    version = version + 1
WHERE sku_id = :skuId
  AND owner_id = :ownerId
  AND location_id = :locationId
```

## 9. Common Reservation Decision

เพื่อไม่ duplicate business rules ให้ refactor internal application flow เป็น:

```text
ReservationExecution.execute(
    InventoryKey inventoryKey,
    long quantity
) -> ReservationDecision
```

`ReservationExecution`:

- อยู่ application layer
- ไม่มี `@Transactional`
- assume ว่า caller เปิด transaction แล้ว
- ใช้ `InventoryBalanceRepository`
- ใช้ existing `ReservationRepository`
- generate `reservationId` เฉพาะ successful first execution
- persist reservation เฉพาะเมื่อ authoritative stock reservation สำเร็จ

conceptual terminal decisions:

```text
SUCCESS(
  reservationId,
  inventoryVersion
)

REJECTED(
  ReservationFailureCode
)
```

### Pre-claim validation boundary

ก่อน authoritative idempotency claim ให้ validate เฉพาะสิ่งที่ทำให้ request
ไม่ใช่ executable business command ตั้งแต่ต้น:

```text
required/null fields
quantity > 0
actorScope non-blank / <= 128
idempotencyKey non-blank / <= 128
```

`QUARANTINED` เป็น valid `StockStatus` แต่เป็น non-reservable business state

ดังนั้น:

```text
stockStatus = QUARANTINED
→ idempotent path claims key
→ ReservationExecution returns INVENTORY_NOT_RESERVABLE
→ terminal REJECTED outcome commits
```

เช่นเดียวกับ authoritative:

```text
INVENTORY_NOT_FOUND
INSUFFICIENT_STOCK
```

stock/business rejection หลัง claim ต้องคืน structured decision

idempotent service ห้าม throw controlled business rejection ก่อน terminal
idempotency outcome ถูก persist

infrastructure exception ยัง throw เพื่อ rollback transaction

normal HTTP path สามารถ map structured rejection เป็น existing application
exception/error contract ได้ เพราะ path นี้ไม่มี idempotency terminal record

ห้ามทำให้ idempotent path กับ HTTP path มี stock rules คนละชุด

## 11. Planned Idempotency Schema

planned logical schema:

```sql
CREATE TABLE vra.inventory_reservation_idempotency (
    actor_scope          varchar(128) NOT NULL,
    idempotency_key      varchar(128) NOT NULL,
    fingerprint_version  smallint NOT NULL,
    request_fingerprint  varchar(64) NOT NULL,

    outcome_status       varchar(16),
    reservation_id       uuid,
    inventory_version    bigint,
    rejection_code       varchar(64),

    created_at           timestamptz NOT NULL,
    completed_at         timestamptz,

    CONSTRAINT inventory_reservation_idempotency_pk
      PRIMARY KEY (actor_scope, idempotency_key),

    CONSTRAINT inventory_reservation_idempotency_fingerprint_version_ck
      CHECK (fingerprint_version = 1),

    CONSTRAINT inventory_reservation_idempotency_fingerprint_ck
      CHECK (request_fingerprint ~ '^[0-9a-f]{64}$'),

    CONSTRAINT inventory_reservation_idempotency_outcome_ck
      CHECK (
        outcome_status IS NULL
        OR outcome_status IN ('SUCCEEDED', 'REJECTED')
      ),

    CONSTRAINT inventory_reservation_idempotency_shape_ck
      CHECK (
        (
          outcome_status IS NULL
          AND reservation_id IS NULL
          AND inventory_version IS NULL
          AND rejection_code IS NULL
          AND completed_at IS NULL
        )
        OR (
          outcome_status IS NOT NULL
          AND outcome_status = 'SUCCEEDED'
          AND reservation_id IS NOT NULL
          AND inventory_version IS NOT NULL
          AND rejection_code IS NULL
          AND completed_at IS NOT NULL
        )
        OR (
          outcome_status IS NOT NULL
          AND outcome_status = 'REJECTED'
          AND reservation_id IS NULL
          AND inventory_version IS NULL
          AND rejection_code IS NOT NULL
          AND completed_at IS NOT NULL
        )
      ),

    CONSTRAINT inventory_reservation_idempotency_reservation_fk
      FOREIGN KEY (reservation_id)
      REFERENCES vra.inventory_reservation (reservation_id)
);
```

`outcome_status IS NULL` อนุญาตเฉพาะ transaction-local claim ระหว่าง transaction
และ DB constraint บังคับให้ transient claim ไม่มี terminal payload ปะปน

`inventory_reservation_idempotency_shape_ck` ต้องใช้ null-safe terminal branches
(`outcome_status IS NOT NULL` ก่อนเทียบ `SUCCEEDED` / `REJECTED`) เพราะ PostgreSQL
`CHECK` ถือ expression ที่ประเมินเป็น `NULL`/`UNKNOWN` ว่าไม่เป็น constraint
violation การเขียน terminal branch เป็นเพียง `outcome_status = '...'` จึงอาจทำให้
transient `NULL` outcome ที่มี terminal payload หลุดผ่าน SQL three-valued logic ได้

POC-02 V2 รองรับ fingerprint schema version `1` เท่านั้น
future version ต้องใช้ explicit migration

required defensive migration tests ต้องพิสูจน์อย่างน้อย:

- `outcome_status IS NULL` + success-shaped payload ถูก reject
- `outcome_status IS NULL` + rejection-shaped payload ถูก reject
- valid transient `NULL` outcome ที่ terminal payload ทั้งหมดเป็น `NULL` ถูก accept
- valid terminal `SUCCEEDED` shape ถูก accept
- valid terminal `REJECTED` shape ถูก accept

exit tests ต้องพิสูจน์ว่าไม่มี committed row ที่ `outcome_status IS NULL`

POC-02 ไม่เพิ่ม:

```text

lease_until
worker_owner
attempt_count for retry engine
TTL

```

## 14. Idempotency Claim SQL

first statement หลัง pre-validation:

```sql
INSERT INTO vra.inventory_reservation_idempotency (
    actor_scope,
    idempotency_key,
    fingerprint_version,
    request_fingerprint,
    created_at
)
VALUES (
    :actorScope,
    :idempotencyKey,
    :fingerprintVersion,
    :requestFingerprint,
    :createdAt
)
ON CONFLICT (actor_scope, idempotency_key) DO NOTHING
RETURNING actor_scope;
```

semantics:

```text
row returned
→ this transaction owns first execution

no row returned
→ identity already resolved/claimed by competing transaction
→ SELECT authoritative row
```

PostgreSQL unique-index conflict/wait เป็น serialization authority

ห้าม add JVM waiting registry

### 14.1 Transaction Isolation Required by Claim Algorithm

claim algorithm นี้ freeze ที่ PostgreSQL:

```text
READ COMMITTED
```

เพราะ flow:

```text
INSERT ... ON CONFLICT DO NOTHING
→ conflict may wait for another transaction
→ subsequent SELECT must use a fresh statement snapshot
→ observe terminal row committed by the winner
```

implementation ต้อง:

- ไม่เปลี่ยน global datasource isolation เพียงเพื่อ POC-02
- verify idempotent transaction จริงว่า `READ COMMITTED`
- มี PostgreSQL integration assertion ของ `transaction_isolation`
- document ถ้า environment override isolation จาก default

ถ้าต้องรองรับ `REPEATABLE READ` หรือ `SERIALIZABLE` ในอนาคต claim algorithm
ต้อง re-review; POC-02 ห้าม assume ว่าสอง-statement flow นี้ equivalent ทุก isolation

## 15. Existing-Key Resolution

หลัง `INSERT ... ON CONFLICT DO NOTHING` ไม่ return owner row:

```sql
SELECT
  fingerprint_version,
  request_fingerprint,
  outcome_status,
  reservation_id,
  inventory_version,
  rejection_code
FROM vra.inventory_reservation_idempotency
WHERE actor_scope = :actorScope
  AND idempotency_key = :idempotencyKey;
```

under required `READ COMMITTED` หลัง PostgreSQL conflict resolution:

```text
INSERT statement resolves winner/loser
+
subsequent SELECT receives a fresh statement snapshot
+
row exists
+
terminal outcome exists
```

resolution:

```text
fingerprint differs
→ IDEMPOTENCY_KEY_REUSED

fingerprint same + SUCCEEDED
→ replay success

fingerprint same + REJECTED
→ replay rejection

row missing
→ fail as unexpected persistence condition

row exists + outcome_status NULL
→ fail as invariant violation
```

ห้าม blindly execute operation ถ้าพบ committed incomplete row

---

### 15.1 Terminal Completion Is Write-Once

runtime `UPDATE` privilege มีไว้สำหรับ transition:

```text
transaction-local NULL outcome
→ terminal SUCCEEDED or REJECTED
```

ไม่ใช่สำหรับ rewrite terminal outcome หลัง commit

completion SQL ทั้ง success/rejection ต้องมี guard อย่างน้อย:

```sql
WHERE actor_scope = :actorScope
  AND idempotency_key = :idempotencyKey
  AND fingerprint_version = :fingerprintVersion
  AND request_fingerprint = :requestFingerprint
  AND outcome_status IS NULL
```

และต้องตรวจ affected/returned row count:

```text
exactly 1 row
→ completion accepted

0 rows
→ invariant violation / stale or already-terminal state
→ do not overwrite terminal result
```

repository ห้ามมี generic method แบบ:

```text
save arbitrary idempotency row
update terminal row without current-state predicate
```

required PostgreSQL integration proofs:

```text
claim → complete SUCCEEDED
→ second completion attempt affects 0 rows
→ original terminal success unchanged

claim → complete REJECTED
→ second completion attempt affects 0 rows
→ original terminal rejection unchanged
```

DB CHECK constraints ป้องกัน invalid row shape ส่วน conditional completion SQL
ป้องกัน invalid state transition

## 16. Terminal Success Persistence

owner transaction success order:

```text
1. claim idempotency identity
2. authoritative stock UPDATE succeeds
3. generate reservationId
4. INSERT reservation
5. UPDATE idempotency row:
     outcome_status = SUCCEEDED
     reservation_id = generated UUID
     inventory_version = returned DB version
     completed_at = transaction clock/time
6. COMMIT
```

expected final shape:

```text
inventory mutation committed
reservation committed
terminal idempotency success committed
```

all or nothing

## 17. Terminal Business Rejection Persistence

owner transaction controlled rejection:

```text
1. claim idempotency identity
2. authoritative reservation decision returns rejection
3. no reservation insert
4. no successful inventory mutation
5. UPDATE idempotency row:
     outcome_status = REJECTED
     rejection_code = stable ReservationFailureCode
     completed_at = transaction time
6. COMMIT
7. caller receives structured rejection
```

same-key same-payload retry:

```text
→ replay same rejection
→ no business re-evaluation
```

new business attempt:

```text
→ requires new idempotency key
```

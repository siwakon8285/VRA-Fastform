## 7. Human identity / OIDC implementation plan

Use the standard Spring Security OAuth2 Client/OIDC support under the existing Boot BOM in **API mode only**. Plan-selected `dev.vra.security.oidc.OidcLoginService`, `TrustedIssuerConfiguration`, and `OneUseAuthorizationRequestRepository` live under `backend/runtime/src/main/java/`; `VraApplication` explicitly imports the API security composition. Configure trusted TEST issuer `https://issuer.poc04.test:8444/realms/poc04`, client `vra-poc04-browser`, callback `https://vra.poc04.test:8443/login/oauth2/code/poc04`, Authorization Code, PKCE S256, state, ID-token nonce, RS256 with RSA keys only, exact audience/client/issuer/time checks. These are **test profile values**, not production IdP selection. Discovery/JWKS may be fetched only from that configured issuer/profile; `jku`, `x5u`, embedded JWK and token-selected URLs are never key authority. No JSESSIONID or framework default persistent browser authority may bypass the PostgreSQL session.

Run a separately operated, digest-pinned **Keycloak TEST container** on the issuer host with Standard Flow, mandatory S256 PKCE and exact redirect. It is outside VRA runtime; its realm/client/users and RSA signing keys are disposable. Real Chromium follows the genuine authorize → callback → code exchange path. A separate adversarial protocol fixture/test adapter supplies malformed token/code/key responses; a network observer proves no fetch to attacker key URLs. Trusted-profile key rotation is accepted only after discovery/JWKS from the same configured issuer. Official fixture/protocol references: [Keycloak containers](https://www.keycloak.org/server/containers), [OIDC endpoints](https://www.keycloak.org/securing-apps/oidc-layers), [client configuration](https://www.keycloak.org/docs/latest/server_admin/).

The server holds a finite, atomic one-use authorization transaction keyed by a random state verifier, binding issuer, client, redirect, PKCE verifier/challenge, nonce, created/expiry and a reviewed local continuation target. Bind initiation to the **same browser** with a separate 32-byte random `__Host-vra_oidc_tx` cookie (`Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, no Domain); store only its SHA-256 digest in the transaction. Callback must match both state and cookie digest, then atomically consume the transaction and clear the cookie. A callback carrying an attacker's valid state/code in another browser must deny without replacing the victim's session. For the single-instance POC, use a bounded process-local transaction repository; restart discards pending login and fails closed. This transaction cookie is **not** browser session authority and makes no multi-instance login claim. `GET /oauth2/authorization/poc04` begins it; `GET /login/oauth2/code/poc04` consumes it once. Allow only fixed local continuation `/poc04/security`; reject absolute, protocol-relative, encoded or double-encoded external targets. A valid token maps issuer/subject through §8 before session issuance. IdP/discovery/JWKS outage creates no session or mapping; existing eligible sessions continue only under §9 policy.

Controlled-clock OIDC transaction TTL is **5 minutes**; valid when `now < expires_at`, expired at equality. ## 9. Browser session lifecycle and verifier design

Plan-selected `dev.vra.security.session.JdbcSessionRepository` and `BrowserSessionService` own PostgreSQL authority. Generate **32 CSPRNG bytes** for a browser bearer; encode unpadded base64url in host-only `__Host-vra_session` (`Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, no Domain). Store only `SHA-256(ASCII("vra-session-v1\n") || raw bearer)` as the indexed 32-byte verifier, computed with the JDK standard `MessageDigest` and PostgreSQL's standard `sha256(bytea)` in the narrow functions that must independently authenticate a human caller. A 256-bit uniform bearer makes the unkeyed digest non-reversible for this bounded POC; the DB-readable digest submitted as a cookie hashes again and fails. No raw bearer is persisted. Compare digests in constant time where an application comparison occurs; indexed database lookup is not claimed constant-time. No custom cryptographic primitive or production KMS is selected. PostgreSQL receives raw bearer bytes **only transiently as a prepared bind parameter in protected validation/function calls**; TEST PostgreSQL must set `log_parameter_max_length=0` and `log_parameter_max_length_on_error=0`, disable application/JDBC parameter logging, and prove those settings plus log/artifact leak scans. A direct SQL caller with only `vra_runtime` and readable session fields cannot select another actor's `session_id` as sufficient proof for a guarded security action; §13 functions verify possession of that actor's raw bearer before attribution or mutation.

TEST-only limits: **absolute 2 hours**, **idle 20 minutes**, measured from issue and last accepted use; `now < both expiry instants` is valid, equality is expired. Use injected `Clock`, not sleeps, for `T−1 second`, `T`, and `T+1 second` cases. A successful login replaces any pre-login identifier. MFA elevation, checker step-up, credential-security change or recovery that changes authority atomically revokes old verifier/generation and issues new bearer, CSRF and assurance generation; logout revokes server row and expires cookie. Account auth-generation mismatch, staff privilege grant and revocation deny every old target session before its next protected action; stale-session rotation cannot copy the new generation into old authority. A valid durable session survives an API process restart; revoked/expired one does not. Store/read outage denies issuance, protected use, rotation and revocation-dependent operation, never authorizes from local cache. Measure lookup/update latency and DB load without HA/capacity claims.

`GET /api/v1/security/session` returns safe current-session metadata only. Tests inspect cookie flags in a real HTTPS browser, old bearer and copied DB verifier replay, fixation candidate, logout, idle/absolute expiry, account disable, privilege grant/revoke, restart and store outage. With at least two pre-grant target sessions, prove both deny after grant commit (including rotation/CSRF bootstrap), no target bearer/cookie/CSRF is returned to maker/checker, and only the target's new valid authentication creates a session carrying the current generation. Never print the bearer in test failure output. `vra.poc04.test` and `issuer.poc04.test` are distinct TEST hosts; using one `localhost` hostname on different ports would leak a host cookie across ports and is forbidden for this proof.

Session issuance, touch/rotation and protected use coordinate with role execution on the same account authority row. Account locks precede session/proposal/approval locks. For protected resource work, the existing narrow `security_touch_browser_session` SECURITY DEFINER function acquires the account `FOR SHARE` lock as `vra_security_executor`, rechecks current generation and touches the session; the application keeps that same JDBC transaction open through its near-mutation check and protected write. The lock survives function return until outer transaction completion; a filter check in an already committed transaction is insufficient. Runtime retains SELECT-only account privileges and never directly acquires that row lock: PostgreSQL locking SELECT requires UPDATE privilege, which is not added to runtime ([PostgreSQL 17 SELECT](https://www.postgresql.org/docs/17/sql-select.html)). Issue/rotate acquires the account write lock inside its guarded function before rechecking the session. For staff execution, preliminary filter validation is read-only and does not leave a checker-only touch lock in the execution transaction; `security_execute_staff_grant` first locks every distinct maker/checker/target account in deterministic UUID order, then locks sessions/proposal/approval and rechecks all authority. Grant holds the target account write lock. A concurrent request linearizes before grant commit or observes the increment and denies; no already-invalid session can refresh itself. Evidence snapshots include target account generation/version, all pre-grant session account-generations, role/proposal/approval/audit linkage and new target-owned login session. Test grant versus session issue/rotate/protected PATCH, duplicate execution, and target equal to maker/checker: their old session becomes stale at the same commit, and the safe grant response still issues no replacement bearer.

## 10. CSRF implementation

## 27. Rollback and recovery behavior

This plan favors **fail closed and forward correction**, not deleting evidence or reversing an applied migration. A V4–V6 failure before commit rolls back that PostgreSQL transaction; a partial external bootstrap or credential fault stops readiness and is corrected by admin with exact role-graph reinspection. For a populated migration failure, preserve the V3 snapshot and Flyway history, diagnose, then apply a new forward migration if any committed change needs correction. Never edit V1/V2/V3 or run Flyway repair to hide drift.

An IdP failure discards pending login but leaves separately valid local sessions under their bounded policy. A session-store or account-policy failure denies protected work until authority recovers; a key compromise revokes dependent sessions/fixture keys before reissue. A staff grant failure rolls back the role, linked protected audit, target auth-generation/version and proposal/approval consumption together. Inspect all four authorities before retrying an unknown outcome; committed grant never reissues the target bearer, and stale target rotation is denied. Revocation keeps its generation invalidation. A webhook key failure creates no receipt/effect; inspect an unknown sender outcome read-only by authenticated eventId/body digest. An early APPLY receipt remains PENDING across restart and after later READY: only read-only eligibility changes, with no pending-event execution/automatic application or reconciliation capability. Observer outages retain protected source segments and sanitized backlog until acknowledged structured capture; loss or mismatch blocks S11 and requires replay from retained source or fresh source-bound probes. Only selected APP event loss remains a residual and never grants permission. After recovery rerun the relevant denial and source-bound gate; no green response alone clears a prior FAIL.

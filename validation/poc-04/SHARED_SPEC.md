## 2. Objective and bounded representative scope

POC-04 must prove one representative security foundation across authentication integration, VRA identity mapping, an opaque browser session/BFF boundary, CSRF, object authorization, privileged MFA/step-up and maker/checker, workload identity, synchronous database privilege hardening, secrets, webhook verification/replay, security events, protected audit, safe errors/logs, and supply-chain/repository governance. The canonical branch scope and exit gate are in [BRANCH_PLAN](../../docs/BRANCH_PLAN.md), [ROADMAP](../../docs/ROADMAP.md), and [SECURITY](../../docs/SECURITY.md).

The proof uses only the minimum identity, membership, protected-record, staff-role-proposal, session, receipt, security-event, and audit state necessary to exercise these boundaries. It must not become a full marketplace implementation. Existing POC-01/02/03 Inventory Reservation, idempotency, migration, outbox, and worker behavior must remain valid. A test-only external OIDC issuer and signed-webhook fixture may supply independently operated protocol counterparts; neither is a production vendor selection or proof of a real provider.

- No claim that representative account/seller checks prove every future domain. Each later sensitive domain must revalidate its own ownership, state, and negative paths.

## 4. Security principles and proof vocabulary

Authentication establishes an external/human identity; authorization decides an actor/action/resource/state/context combination. An identifier is a lookup key, not a grant. Staff is scoped, not superuser. Workload and database principals are separate from people. A private network grants no identity. Frontend hiding does not enforce backend policy. MFA is a time-bounded assurance input, not permanent elevated authority. An HTTP `401`, `403`, or `404` is response evidence, not complete denial proof.

**Security claim without bypass/negative proof = NOT VERIFIED.** Each material control must trace: requirement → threat → trust boundary → invariant → minimum authority → selected semantic control → bypass/failure cases → positive proof → negative/adversarial proof → authoritative evidence → residual/nonclaim. Section 27 is the executable gate index for that trace.

For a denied mutation, compare authoritative rows and versions immediately before and after the attempted denial: protected business resource, membership/role, proposal/approval, session, idempotency, outbox, webhook receipt, and audit where applicable. A permitted append of a denial security event or audit attempt is an **explicit expected delta**, never hidden inside a claim that all database state is unchanged. Tests must distinguish response status from committed state, and must use PostgreSQL where PostgreSQL decides the invariant. [TESTING](../../docs/TESTING.md) defines final-state assertions and PASS/NOT VERIFIED semantics.

## 6. Provider-neutral identity mapping and account lifecycle

**Accepted bounded POC invariants:**

1. The external identity key is the tuple `(validated issuer, immutable subject)`, never email, display name, phone, or an unverified claim. The tuple has at most one current intended VRA-account binding. Database uniqueness plus an atomic linking operation must resolve races; a duplicate/conflicting binding denies without moving either account.
2. A VRA account has a VRA-controlled stable ID and explicit `ACTIVE`, `LOCKED`, `DISABLED`, or `CLOSED` state. Only `ACTIVE` may create or use an ordinary session. Transition away from `ACTIVE` invalidates usable sessions and privileged assurance before another protected action. State changes are authorized and audited.
3. POC fixtures may establish one reviewed initial subject binding for each representative account. This does **not** prohibit multiple external identities per account in a later reviewed linking model. Self-service link, unlink, merge, and recovery are out of bounded POC scope. If invoked without an authorized workflow, they deny with mapping and membership unchanged. Future support must prove possession of both sides or a separately reviewed recovery authority; email equality is insufficient.
4. A person acting for another business subject retains the actor identity. Seller membership is an independently checked relationship with state and scope, not a role claim from an IdP. A role assignment is independently revocable. Privileged assurance belongs to an actor/session/action context and expires; it is not stored as a permanent account privilege.

Positive proof: one valid issuer/subject maps to the intended `ACTIVE` account and its current memberships. Negative proof: wrong issuer, missing subject/mapping, mapping collision, concurrent linking, locked/disabled/closed account, email-only match, removed membership, and stale session all deny. For each denial, snapshot mapping, account, membership, session, and target state; assert only expressly expected security telemetry changes. Future self-service link/recovery policy is **DEFERRED — OUT OF POC** under U2 and is not silently selected by this bounded rule. [PRODUCT](../../docs/PRODUCT.md) and [SECURITY](../../docs/SECURITY.md) separate authentication from business eligibility.

## 7. Authentication integration contract

**Accepted browser POC profile:** a standard OIDC Authorization Code flow handled at the VRA server/BFF boundary, with an exact registered redirect target, transaction-bound `state`, PKCE, and `nonce` for an ID token. Accepted issuer authority is configured and trusted by VRA before a login starts; it is never learned solely from an untrusted request, token, or callback. Discovery, JWKS and verification keys derive only from that trusted issuer configuration/profile. A token/header-supplied arbitrary key URL (`jku`, `x5u` or equivalent) or embedded JWK cannot establish verification authority; any profile that requires such a source must first freeze and constrain it as trusted authority. Accepted signing algorithms and key types are explicitly allowlisted for the trusted profile. Unsigned material, algorithm/key-type confusion, an unknown/untrusted key, invalid signature, wrong issuer, wrong audience/client, expiry or wrong token use deny. Trusted-profile key rotation may accept only keys resolved through that authority, never an attacker-selected fallback.

Each authentication transaction has finite expiry and one-time consumption. Its server-held state binds the expected configured issuer, client, registered redirect target, `state`, `nonce`, and PKCE verifier/challenge context; callback and token results must match that transaction before a VRA session is issued. A post-login continuation/return target is a reviewed local target, not an arbitrary external URL; reject absolute, protocol-relative and encoded redirect bypasses. A successful external login creates only a VRA session for an eligible mapped account; it grants no protected-resource operation by itself. No custom authentication protocol or production IdP vendor is selected. The protocol fixture must run outside the VRA runtime and exercise real browser redirect/callback navigation and token validation; unit-mocking a successful principal cannot satisfy S1.

Required negative proofs: absent/mismatched/replayed/expired transaction or state; wrong callback/redirect or PKCE context; missing/wrong nonce; reused authorization code or authorization transaction; unconfigured issuer or untrusted discovery/JWKS; attacker-controlled `jku`/`x5u`/embedded JWK or equivalent; unsigned or disallowed/confused algorithm/key type; unknown key; wrong issuer, audience or client binding; bad signature or expired material; external/open-redirect return target; missing mapping; and locked/disabled/closed account. Each must create no usable session, no accidental mapping, and no protected business mutation; consumed/expired transaction state and permitted denial telemetry are separately recorded as expected deltas. All named selected-flow bindings require proof; only an additional profile-dependent element may be marked inapplicable with an exact protocol reason and equivalent relevant negative. IdP outage denies new login and re-authentication; it cannot create a local success fallback.

Future native mobile direction is Authorization Code + PKCE as a public client with platform secure storage and no embedded confidential secret. This POC does not build or claim a mobile client. [SECURITY](../../docs/SECURITY.md) and [DESIGN](../../docs/DESIGN.md) establish these directions. The provider-neutral test profile is accepted under U1; a commercial IdP remains **DEFERRED — OUT OF POC**.

## 8. Representative authorization model

The policy inputs are the canonical **RBAC + ownership + resource state + organization/seller relationship + context + risk + approval requirements**. The backend must evaluate the relevant inputs close enough to mutation to prevent stale-ownership or approval TOCTOU bypass; a controller/UI check alone is insufficient. A testable policy matrix must record at least actor, role, resource, action, owner, organization membership, state, assurance, approval, context/risk, and expected result.

**Accepted bounded protected model:** two kinds of small POC protected record using a common authorization contract: (a) a private account-owned record, and (b) a distinct organization/seller-owned record. Each has a stable ID, authoritative owner reference, state `ACTIVE` or `CLOSED`, version, and a bounded nonsensitive label. The only ordinary mutation changes the label on an `ACTIVE` record and increments its version; it cannot alter owner, organization or state. `CLOSED` denies mutation. An organization membership fixture authorizes the seller record. The policy matrix records ordinary context/risk and no approval for this label change; the privileged role grant in section 12 records elevated context/risk and required approval. The records carry no commerce, Order, Offer, Payment, or inventory ownership semantics. The actual schema/path/names belong in the implementation plan; these ownership/state/action semantics are accepted for the bounded POC. In particular, Inventory `ownerId` is **not** assumed to equal `sellerId`.

Required outcomes: Customer A's own eligible record allowed; Customer A → B denied; Seller A's own eligible seller record allowed; Seller A → B denied, including a forged `sellerId`; staff with the wrong operation/data scope denied; privileged action without valid assurance denied. For every denied mutation, authoritative record, ownership, version, membership, role and approval state remain unchanged, apart from the separately expected denial event. A denied read returns no foreign content. These representative results do not generalize automatically to later product domains. These protected-record and policy semantics are accepted under U5; exact schema and the matrix artifact belong in the implementation plan.

## 10. Browser session authority and lifecycle

**Accepted bounded POC choice U3:** PostgreSQL-backed server-side session records for this bounded POC, using the already operated authoritative database. This bounded decision still requires ADR review at the later authorized checkpoint and makes no production capacity claim. Redis is deferred absent measured need. A process-local-only session authority cannot satisfy a multi-instance/restart claim without a separate review.

The browser receives only a high-entropy, unpredictable opaque bearer identifier in a cookie with `Secure`, `HttpOnly`, narrow path/domain, and bounded absolute and idle expiry. Accepted bounded `SameSite` policy: `Lax` for a first-party top-level redirect/BFF flow; a cross-site or embedded flow requiring another value needs separate threat review and browser proof before adoption. Persistent session authority stores a non-reversible, non-reusable verifier or an equivalent design, never a directly reusable copy of the browser bearer; disclosure of session-table readable fields alone must not yield a cookie credential that authenticates. The server stores authoritative account ID, current session generation, assurance context, issue/use/expiry/revocation state, and only metadata required for security. Raw bearer material exists only transiently where request validation or cookie issuance requires it, and must not enter application/security/audit logs, errors, test evidence or final artifacts. Both lifetime bounds must be finite and testable with a controlled clock. POC durations are fixed in the later plan/test configuration, not asserted as production tuning numbers here. The browser TEST surface must honor `Secure`; a test-only cookie downgrade cannot prove the production-facing attribute.

Login must replace any pre-authentication identifier. Step-up/elevation or recovery that changes authority atomically invalidates the old persistent verifier and issues a new bearer/verifier generation; the old ID, CSRF token and assurance cannot follow it. Logout revokes server-side authority and clears the browser cookie. Account disable, credential-security change, suspicious-login response, and staff privilege revocation must make the affected session or elevated capability unusable before the next protected decision according to a tested policy. An unknown, expired, revoked, or pre-rotation bearer/verifier denies. A server restart must not resurrect revoked/expired state; a valid session may survive restart only if the selected durable state says it remains valid. When the session store cannot be consulted, protected actions deny rather than using a local success fallback.

Positive proof: valid session operates within account policy and survives a POC restart if still valid. Negative proof: fixation candidate after login, old ID/verifier after atomic rotation, replay after logout, idle/absolute expiry, account disable, privilege revoke, and unavailable store all deny with business state unchanged. A read-only session-database fixture must show that copied readable verifier/metadata cannot be submitted as a usable browser cookie, without printing any raw bearer. Inspect session-table readable fields, logs, errors, evidence and final artifacts for absence of raw bearer. Multi-instance behavior is claimed only if tested with two actual instances against one authority; otherwise it is a nonclaim. PostgreSQL adds DB load and availability coupling; recovery and latency evidence must be recorded. Session architecture requires ADR review classification in section 26. [SECURITY](../../docs/SECURITY.md), [ROADMAP](../../docs/ROADMAP.md).

## 11. CSRF semantics

Every cookie-authenticated state-changing API operation must use an unsafe HTTP method (`POST`, `PUT`, `PATCH`, `DELETE`, or another actual method that mutates state) and enforce a session-bound anti-CSRF proof. A mutating resource `GET` is forbidden; the OIDC top-level callback is separately bound by single-use `state`/`nonce` rather than treated as a general resource mutation. The accepted synchronizer token is unguessable, bound to the authoritative session generation, obtained through a same-origin safe bootstrap response, sent in an explicit request header on unsafe calls, and invalidated on session rotation/revocation. The bounded origin policy is same-origin by default, denying unsolicited credentialed cross-origin requests; any explicit additional origin needs independent review and a narrow allowlist. CORS is not authorization and cannot weaken token validation. `SameSite` alone is insufficient. JSON, form, multipart, and other actually accepted content types must not create a parser/method bypass. Explicit header transport and the same-origin POC policy are accepted under U4; exact deployment origins and any additional origin require review before use.

Positive proof: valid session, permitted origin, valid session-generation token, and authorized action succeed. Negative proof: missing token, invalid token, another session's token, old token after rotation, logged-out/revoked session, disallowed origin, alternate accepted content type, and method-override/parser attempt deny. An unauthenticated/revoked session receives the safe authentication denial; a valid session with bad CSRF proof receives a stable CSRF denial. For every denied mutation, resource, approval, session authority, idempotency and outbox state remain unchanged except for an explicitly expected security event. Spring defaults cannot substitute for executable proof. [SECURITY](../../docs/SECURITY.md), [TESTING](../../docs/TESTING.md).

## 12. Representative privileged action

**Accepted bounded POC choice U6:** a narrowly scoped grant of a privileged *staff security role* to another staff account. This operation is named in canonical security examples and stays inside identity/security scope rather than importing a Payment or seller business domain. The bounded role proposal records target staff account, exact role, data/operation scope, maker, reason, proposed change version/digest, creation/expiry, and state. It must not create a public staff-signup path.

The bounded maker requirement is an active, appropriately scoped MFA-authenticated staff session at proposal time; the maker submits a reason and does not need a separate fresh step-up for this representative proposal. The checker must be a distinct active staff actor with the required operation/data scope and must complete a fresh independently validated, context-bound step-up before execution, tied to the current checker actor/session and exact approval context. The checker assurance has finite expiry and cannot be transferred to another operation or target. Approval binds the exact immutable proposed change and version. A changed proposal invalidates prior approval. Execution checks maker/checker separation, current roles/account state, current proposal, unexpired approval and checker step-up close to the authoritative role mutation, then atomically applies at most the approved change and appends protected audit evidence. Revocation of maker/checker privilege or session before execution denies. An application-set boolean is not MFA evidence. The bounded maker/checker policy is accepted under U6; numeric assurance lifetime and the independently validated test factor/challenge profile belong in the implementation plan. WebAuthn/passkeys remain strategic direction, not a selected production provider.

Positive proof: MFA-authenticated maker and distinct authorized checker with an independently validated fresh factor/challenge, exact proposal and reason produce one role change and attributable protected audit. Negative proof: maker without MFA; maker self-approval; checker lacking permission or scope; fake/replayed/wrong-actor/wrong-session factor assertion; absent/expired/wrong-context step-up; changed proposal after approval; expired approval; revoked maker/checker/session; target account ineligible; and direct execution without approval all deny. Snapshot proposal, approval, assurance, staff roles/memberships, target and audit before/after; only expected denial evidence may append. [SECURITY](../../docs/SECURITY.md), [PRODUCT](../../docs/PRODUCT.md).

## 14. Synchronous PostgreSQL privilege review and selected claim boundary

Current V1 grants: `vra_runtime` has `SELECT, UPDATE` on `inventory_balance` and `SELECT, INSERT` on `inventory_reservation`. Current V2 grant: table-wide `SELECT, INSERT, UPDATE` on `inventory_reservation_idempotency`. These are the actual synchronous direct-SQL paths; application-level predicates do not constrain arbitrary SQL using the same credential.

**Accepted bounded choice U7: guarded V2 option A.** Narrow V2 claim and completion through operation-specific guarded PostgreSQL capabilities, revoke direct table-level terminal-row `UPDATE`, and prevent direct terminal-shaped `INSERT` under `vra_runtime`. The guarded transition accepts only a matching transient identity/fingerprint and an exact NULL→`SUCCEEDED` or NULL→`REJECTED` shape once, within the existing business transaction. Every granted callable operation must reject mismatch against the stored actor scope and fingerprint, wrong state or reservation/result shape, and repeated completion; actual direct function calls, not just application methods, are adversarial tests. A column-level `UPDATE` alone is insufficient because it still permits rewriting allowed terminal fields. A trigger or another mechanism is acceptable only if PostgreSQL positive/negative evidence shows equivalent control; RLS is not automatic. Do not reuse the async executor owner for synchronous work without a reviewed role/ownership decision. No generic `set_state` function is permitted.

If the guarded capability uses `SECURITY DEFINER` or an equivalent privileged PostgreSQL object, its owner must be a dedicated, narrowly empowered identity (`NOLOGIN` where appropriate), separate from runtime/migrator/async executor. Freeze a fixed safe `search_path`; fully qualify trusted relations where appropriate; permit no attacker-controlled dynamic SQL; revoke `PUBLIC` execution; and grant `EXECUTE` only to exact intended caller roles. Untrusted callers must have no `CREATE` in any schema able to shadow referenced objects. Review function/catalog owner, definition, `SECURITY DEFINER` status, ACLs, schema ownership/`CREATE` grants, role membership and all direct/transitive `SET ROLE` edges. Execute actual wrong-caller, shadow-object and granted-function bypass SQL, not merely inspect source or application behavior; denied attempts must leave authoritative rows unchanged. A trigger or other chosen mechanism bears demonstrably equivalent no-bypass obligations. **S8 cannot PASS if the hardening mechanism creates a new privilege-escalation path.**

Inventory every post-hardening direct grant, including V1 `inventory_balance SELECT/UPDATE`, V1 `inventory_reservation SELECT/INSERT`, and V2 `inventory_reservation_idempotency SELECT/INSERT/UPDATE`, with the exact retained/revoked rights and callable replacements. Any retained V2 direct `INSERT` must be proved unable to forge a terminal row; a retained direct `UPDATE` must be proved unable to rewrite one, or S8 fails. This bounded choice does **not** claim database-enforced per-human or per-seller row confidentiality, compromised-runtime confidentiality, or complete first-result business authenticity under a compromised `vra_runtime` credential. Retained direct `SELECT` can expose rows outside a human/seller scope to a holder of the shared runtime credential; a caller holding that credential can invoke granted guarded operations with chosen inputs; retained V1 balance `UPDATE` and reservation `INSERT` can fabricate supporting business state outside the application path. No silent broad-grant retention may accompany an unrestricted direct-SQL isolation claim.

Any change is forward-only: preserve V1/V2/V3 source bytes, Flyway checksums/history, existing transient/terminal rows, runtime/migrator separation, and POC-03 async role behavior. Test fresh migration and an actual populated V3→new-version upgrade, rerun/validate, correct function/catalog owner/ACL/schema/role graph, legitimate positive operations, denied arbitrary terminal `UPDATE`, forged terminal `INSERT`, wrong-caller/function/search-path/shadow bypass, role escalation, and authoritative unchanged state. ## 15. Idempotency and POC-03 compatibility

The selected V2 hardening must preserve: one legitimate first claim; successful completion; business rejection; same-key/same-fingerprint replay; fingerprint conflict; concurrent same-key arbitration; rollback and lost-result recovery; and POC-03's atomic first-success reservation, terminal idempotency result, integration event and initial delivery. The trusted public `actorScope` must derive from verified VRA account, operation and business scope. A request ID is correlation data, never idempotency identity. [POC-02 results](../poc-02/evidence/RESULTS.md), [POC-03 results](../poc-03/evidence/RESULTS.md).

Existing terminal result immutability is claimed only if no direct DML or granted callable operation under `vra_runtime` can rewrite the terminal row. Direct terminal-shaped table insertion must be denied. Review every retained V1/V2 direct `SELECT`, `INSERT` and `UPDATE` grant under section 14 before stating the bounded S8 claim. This does not certify that a fully compromised runtime credential cannot read cross-scope rows, fabricate new supporting V1 business state, and then invoke an otherwise permitted first-completion operation; those confidentiality and first-result authenticity residuals are disclosed in section 14. Positive application tests alone are insufficient. Cross-account key reuse through the authenticated HTTP path must not reveal another actor's stored result. For each denied direct SQL, direct function-call misuse or cross-scope replay, compare idempotency row, Inventory balance, Reservation, outbox event/delivery, and version/count snapshots. Retention/expiry policy remains outside this bounded proof unless necessary for session/authorization safety; do not imply an untested purge lifecycle.

## 16. Provider-neutral inbound webhook contract

The POC verifier consumes **exact received raw body bytes**. The independently operated **TEST-ONLY** fixture uses scheme **VRA-HMAC-SHA256-V1** for HTTP **POST /api/v1/security/webhooks/fixture**. The actual method and path must match those literals; an alternate method, path, encoded path alias, or query variant denies. Required single-value metadata is `keyId`, `timestampEpochSeconds`, `eventId`, and `signature`. Missing metadata or a duplicate required header/metadata value denies before verification. `keyId` and `eventId` are nonempty strict UTF-8 values without CR or LF. `timestampEpochSeconds` is a canonical, unsigned ASCII base-10 Unix epoch seconds value with no sign, whitespace, leading zeros except `0`, or overflow. `signature` is exactly 64 lowercase hexadecimal characters; malformed encoding denies.

The signed bytes are **exactly** this concatenation, where LF is one byte `0x0A` and the final segment is the received body without parsing, reserialization, or newline normalization:

~~~text
ASCII("vra-webhook-v1\n")
+ ASCII("POST\n")
+ UTF8("/api/v1/security/webhooks/fixture\n")
+ UTF8(keyId) + LF
+ ASCII(timestampEpochSeconds) + LF
+ UTF8(eventId) + LF
+ exact raw request body bytes
~~~

`signature = HMAC-SHA-256(testSecret, signedBytes)`, encoded on the wire as lowercase hexadecimal. The verifier selects `testSecret` only through the configured, authorized `keyId` and compares the decoded 32-byte MAC with the recomputed MAC in constant time. Each fixture test secret is high entropy, injected at execution, never checked into source or evidence, and is **not** a production key, KMS, secret-authority, provider, or signature-scheme decision. A bounded key overlap must accept an authorized new key, then reject the revoked old key; an unknown `keyId`, wrong key, or unavailable key authority cannot authenticate an event.

The freshness window `W` is finite, positive, and configurable for this POC. With controlled clock `now`, a well-formed timestamp is fresh exactly when `now - W <= timestampEpochSeconds <= now + W`; older and further-future timestamps deny. The implementation plan may set the numeric POC `W`; it is not a production tuning recommendation. The actual method/path, single-value metadata, authorized key, signature, and freshness must succeed **before any body parse, durable accepted receipt, or authoritative effect**. `eventId` is untrusted until those checks succeed. Invalid verification returns a uniform safe denial and does not log the secret, signature, or body.

Only an authenticated fresh event may create a durable receipt or authoritative effect. A unique authenticated `eventId` receipt must persist a collision-resistant fingerprint of the exact verified raw body bytes (SHA-256 under this fixed method/path), or equivalent authenticated receipt evidence. The key, timestamp, and signature are authentication envelope fields, not event-content identity: a fresh valid redelivery with the same authenticated `eventId` and identical raw body is a legitimate duplicate, acknowledged with **no second authoritative effect**, including when re-signed under an authorized overlapping key. The same authenticated `eventId` with different authenticated raw-body content is a conflict and denies without changing the original receipt or effect. A stale, future-invalid, revoked-key, or otherwise invalid replay denies; an exact fresh duplicate is deduplicated. This is a bounded no-second-effect claim, not exactly-once delivery. A verified out-of-order event is durably recorded as pending, applies no state-incompatible effect, and becomes eligible only after its prerequisite state is observed or an explicit reconciliation decision is recorded. A delayed event outside the freshness window is not accepted for effect. Unknown external outcome must not be mislabeled a retry-safe failure. Verifier/key authority outage causes no effect and a retry-safe failure; exact provider-specific HTTP retry mapping is deferred.

Positive proof: one valid new event; an exact legitimate duplicate with one receipt/effect identity and no second effect; bounded key overlap, new-key acceptance, and old-key revocation. Required negative proof: missing metadata; duplicate required header/metadata value; malformed timestamp; unknown `keyId`; wrong key; revoked key; altered exact raw body; altered actual method/path; altered `eventId`; bad signature; stale and future-invalid timestamps at controlled-clock boundaries; replay; and the same authenticated `eventId` with different authenticated content. Also prove malformed authenticated payload, delayed delivery, and out-of-order state behavior. For every rejected event, authoritative receipt, business, idempotency, outbox, and audit state remain unchanged except expected security telemetry. This construction freezes **TEST FIXTURE semantics only**; provider-specific webhook authority, production key custody, and production signature adaptation are **DEFERRED — OUT OF POC** under U9. [DESIGN](../../docs/DESIGN.md), [SECURITY](../../docs/SECURITY.md), [TESTING](../../docs/TESTING.md).

## 18. Security-event semantics

A security event is structured detection/investigation evidence, separate from a protected audit record, domain event, integration event, or ordinary rotating application log. The POC event vocabulary must cover: authentication success and failure; authorization denial and repeated/probing pattern; step-up challenge/success/failure; privilege proposal/grant/revoke; session rotation/revocation; webhook verification failure/replay; and audit tamper attempt where applicable. Each event records a safe actor/account or workload reference when known, event type, outcome, timestamp, request/correlation ID, target class/reference only when safe, and risk context needed for review. It must not carry passwords, bearer/session tokens, CSRF tokens, signatures, raw webhook body, full PII, or private foreign-resource content. An expected denial event may be appended even when a business mutation is denied. Negative proof must assert event type, correlation and data minimization; adversarial repeated forbidden access must be distinguishable from an ordinary not-found without disclosing the foreign object to the caller. Delivery/failure of telemetry must not grant authority. Any requirement for durable security-event capture in a critical decision must be included in the transaction or a reviewed failure path; otherwise record the loss risk as a nonclaim. ## 19. Protected audit semantics

The minimal audit record for a significant privileged/security action has actor ID, actor type, business subject if distinct, action, target, reason, result, authoritative timestamp, request/correlation ID, and proposal/approval linkage where applicable. Actor, subject and action attribution derive from authenticated server-established actor context and authoritative proposal/target state, never client-supplied actor/subject/action fields. A shared `vra_runtime` database credential alone cannot establish which human acted; application context and protected proposal linkage must provide the bounded attribution proof. A safe before/after reference or delta may be included without secret or unnecessary PII. A staff-assisted action must preserve staff actor separately from customer/seller subject. Audit is distinct from application logs and outbox integration events. [PRODUCT](../../docs/PRODUCT.md), [DESIGN](../../docs/DESIGN.md), [SECURITY](../../docs/SECURITY.md).

Protected audit must append for proposal, approval/rejection, privilege execution/revocation, and relevant denial/tamper attempts. Routine `vra_runtime` business capability must not have arbitrary `UPDATE`, `DELETE`, or `TRUNCATE` of history. The selected append mechanism must have attributable caller, bounded content, independently testable reads, and a PostgreSQL permission/immutability check. Positive test: authorized action and expected audit append commit together at the chosen boundary. Negative tests: supply forged actor/subject/action values through the application API and attempt direct SQL audit-row forgery plus runtime/worker/staff-API edit/delete of another actor's audit; each must deny with the expected SQLSTATE or policy result while existing audit and business state remain unchanged, with the expected tamper security event separately counted. A committed role change without required audit fails S11. Retention duration is deferred because canonical documents do not set a number; ownership, access and mutation protection cannot be deferred.

## 20. Safe HTTP error, disclosure, and enumeration contract

All representative security failures return stable public code, safe message and server-controlled request ID; internal exception type, SQL, table name, stack trace, filesystem/internal path, provider host/key, credential, token, session identifier, CSRF value, signature, and private foreign-resource details must not appear in response or log. Logs may contain a sanitized request route, safe error category, operation, outcome and request ID; raw URI paths containing sensitive IDs must be reviewed and minimized. The current [request filter](../../backend/runtime/src/main/java/dev/vra/platform/web/RequestIdFilter.java) and [generic error handler](../../backend/runtime/src/main/java/dev/vra/platform/error/GlobalApiExceptionHandler.java) provide only a narrow earlier baseline.

**Accepted bounded representative response policy:** unauthenticated protected API → `401 AUTHENTICATION_REQUIRED`; foreign private account/seller record and nonexistent ID → the same `404 RESOURCE_NOT_FOUND` body; actor lacking known operation/role/step-up authority → `403 FORBIDDEN` without target existence detail; valid session with invalid CSRF → `403 CSRF_INVALID`; invalid OIDC callback → `400 AUTH_FLOW_INVALID` regardless of which validation failed; invalid webhook authenticity/freshness → `401 WEBHOOK_UNVERIFIED` for wrong key, altered body and stale timestamp alike; unexpected failure → `500 INTERNAL_ERROR`. Each uses a safe message and server request ID. Exact provider-specific webhook retry mapping remains deferred; the representative fixture must follow this POC contract. Account login/recovery responses must not expose whether an email or account exists. Tests compare foreign/not-found bodies and timing categories sufficiently to detect obvious existence leakage, without claiming perfect timing indistinguishability. No response policy replaces unchanged-state or audit/security-event assertions. [SECURITY](../../docs/SECURITY.md), [TESTING](../../docs/TESTING.md).

## 28. Test-layer matrix and non-substitution rule

| Layer | Required contribution | Cannot substitute for |
| --- | --- | --- |
| **A — source/architecture/static** | Map public routes, DTO binding, dependency graph, identity/role paths, migration/SQL objects, scope and policy matrix. | Executed denial and DB state. |
| **B — unit/policy** | Exhaust representative actor/action/owner/state/assurance/approval decisions and expiry with controlled time. | PostgreSQL ACLs or real HTTP filters. |
| **C — PostgreSQL/Testcontainers** | Fresh/upgrade migrations, uniqueness/transactions, roles/ownership/grants, direct SQL `42501` and other exact SQLSTATE, audit protection, authoritative snapshots. | External HTTP contract or browser cookie behavior. |
| **D — Spring HTTP/security-filter integration** | Callback/filter/session/CSRF/authz/error/header behavior and absence of filter-chain bypass. | DB privilege proof or independently bound external client behavior. |
| **E — Bruno black-box** | Actual externally reachable API contract, own/foreign/staff/CSRF/revocation/webhook/replay cases with reproducible CLI. | Unit, DB, fault or browser semantics. |
| **F — real-browser E2E** | Required for the selected POC OIDC redirect/callback, actual `Secure`/`HttpOnly`/`SameSite` cookie behavior, login session establishment, rotation, logout/revocation and CSRF on a minimal genuine auth/BFF surface; privileged step-up F only if browser-exposed. | C/D/E; absent genuine browser session/BFF surface leaves S1/S4/S5/S14 browser-specific claims NOT VERIFIED, never N/A while the selected browser boundary claims PASS. |
| **G — adversarial/fault** | Tamper/replay, dependency outage, concurrency/TOCTOU, wrong credentials, privilege probing, failed audit/secret/key cases. | Ordinary positive cases. |
| **H — artifact/leak/supply-chain inspection** | Source/docs/log/artifact secret scan, dependency/action provenance, wrapper and JAR contents, safe error/log markers. | Runtime authorization behavior. |
| **I — final bound execution/source binding** | Tie exact reviewed source, spec/plan, tests, outputs and artifacts to one final execution and independent review. | Any missing layer-specific test. |

S0–S15 list the required layers per gate. The implementation plan may add cases but cannot remove a layer or a mandatory negative without a reviewed spec change. A `401`/`403`/`404`, green unit suite, or CI badge alone is not a security proof. [TESTING](../../docs/TESTING.md).

## 29. Future final bound execution and evidence

This section defines a future requirement; **nothing here is executed by freezing this specification**. Before a POC-04 PASS claim, capture:

1. Exact approved/frozen spec and implementation-plan bytes, accepted ADR decisions or documented no-ADR findings, branch/HEAD/tree, tool versions, PostgreSQL version, disposable TEST identity, and a source manifest covering main source, tests, migrations, configuration, workflow and collection.
2. Privileged browser step-up proof is required only if that flow is browser-exposed; absence of a genuine browser session/BFF surface leaves S1/S4/S5/S14 NOT VERIFIED, not N/A.

## 30. Exit criteria and nonclaims

POC-04 may be reported **PASS** only when S0–S15 individually PASS, every POC-critical part of U1–U13 has been accepted before freeze (only out-of-scope production/vendor portions may be explicitly deferred), material ADRs are reviewed/accepted before the affected implementation, zero known critical security blockers remain, and section 29 evidence is complete and independently reviewed. A gate cannot PASS through a known bypass plus a disclaimer; its control or bounded claim must be revised and reviewed. The final report must state residual V1 direct-SQL power, any storage/provider/runner risk and any policy not tested. [ROADMAP](../../docs/ROADMAP.md), [SECURITY](../../docs/SECURITY.md), [TESTING](../../docs/TESTING.md).

POC-04 PASS will **not** imply production readiness, production IdP/provider selection, complete marketplace authorization, real mobile implementation, Payment/Refund/payout security, HA/SLO/capacity, multi-region behavior, selected production secret/KMS architecture, permanent Redis adoption, full future audit retention, or automatic inheritance of representative proofs by later domains. Those need their own authority, implementation and evidence.
